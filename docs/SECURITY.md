# Security model

CuliBox starts shells and agents on your machine, so authentication is never optional.

## What is protected, and how

- **Login.** Either a generated token (printed once in a URL, kept at `0600` in the data root) or a password from the env var named by `password_env`. Failed logins are throttled. Browsers get a signed 30-day cookie; delete `cookie.secret` to log everyone out. Named, revocable device tokens (bearer tokens, made in **Settings → Access**) exist for programmatic clients and are stored as hashes.
- **Network exposure.** The default bind is loopback. Binding all interfaces is refused unless `allow_public` is set. Requests whose `Host` header is not in the allowlist are refused (DNS-rebinding defence), and state-changing requests are checked for same-origin.
- **Containment.** The boxed tier described in [Features › Contain](FEATURES.md#contain). Roughly, containment comes from what is absent inside the box. The hardening flags are the smaller part. A box cannot reach services on the host's loopback, other than CuliBox's own credential broker and the egress proxy; on macOS CuliBox checks this on every new box and refuses the box if the check fails.
- **Cloud access.** The broker mints credentials only for live boxed sessions and for host sessions of a bound profile (a guardrail, see below), with a per-spawn token, rate limits, and a 15-minute lifetime. The role is capped by `ReadOnlyAccess`, and a generated session policy denies reading S3 objects (outside an allowlist you set per connection), Secrets Manager values, SSM parameters, DynamoDB items and KMS decrypt. Trust is limited to the SSO permission sets you name and requires a `SourceIdentity` of `agentbox-*`. Broker tokens are bound to the box that holds them: a token presented from any other box is refused and audited (`denied_box`). On macOS the binding is weaker than on Linux: a process running as you that holds a token can claim to be its box, though other accounts on the Mac cannot, even while CuliBox is stopped (see [docs/MACOS.md](MACOS.md#token-binding), which also covers accounts that can read loopback traffic, and what this assumes about the host agent's dial address). Create the role with [docs/aws/agent-role](aws/agent-role/README.md). Each AWS connection's base role is checked for write access when a session starts (see [Several AWS accounts in one session](AWS.md#several-aws-accounts-in-one-session)). The opt-in [SSO role directly](AWS.md#sso-role-directly-opt-in) mode has none of these protections: it hands the agent your read-only permission set's own credentials, so it is allowed only after a read-only gate passes on every mint, its credentials keep the expiry of your SSO role credentials (up to N hours), CloudTrail shows you, and the gate cannot see resource-based policies. Prefer the agent role. A host session of a bound profile is served too, but there the bindings are the default credentials, not a limit: the agent keeps your full access to this machine and the broker cannot stop it from using that (see Known limits below).
- **Service.** `culibox service install` (opt-in) runs `culibox serve` as a `systemd --user` unit or a LaunchAgent of your own user. The unit holds no secret: the program path, `serve` and `-config`, `PATH`, the locale and the data-root variables. It refuses a `bind_addr` that is not loopback and refuses `password_env` rather than store a password, at install and again at every start of the service (`serve -service`), so a later config edit stops the service instead of exposing it. Its log (`service.log`, created `0600`) holds the startup login URL with the token, so it is as secret as `login.token`. On Linux without lingering, logging out stops the service and kills its running sessions (see [INSTALL.md](INSTALL.md#run-as-a-service)). Install replaces, and uninstall removes, only a file that carries CuliBox's marker, and never through a symlink.
- **Store.** Values held in the [store](STORE.md) are encrypted against disk snapshots and backups. While it is unlocked, host-tier agents can read them; boxed agents cannot.
- **Static tokens.** A bound token is fetched per command through the broker, is audited, and reaches only the hosts its entry names. The agent can still read it, and it is long-lived and not revoked when the session ends. On Host the same wrapper fetches it, but the agent also has your own access to the machine. See [Static tokens for agents](STATIC-TOKENS.md).
- **Links an agent shows.** A link in a terminal (plain text or OSC 8), in a rendered markdown file or Ctrl/Cmd+clicked in the Files editor opens only after an "Open this link?" dialog, and only for `http` and `https`. The dialog shows the full address with the real host in bold, an international host in both its Unicode and its `xn--` form, and a warning line for each local check that fires: an IP or private address, non-ASCII letters, a user name before `@`, a non-default port, plain `http`, a known link shortener, another address carried inside the link, or a host one letter away from (or starting with) a host you trust. CuliBox does not check where a link leads: there is no reputation or phishing lookup, and the absence of warnings does not mean a link is safe. Your browser's own check (Safe Browsing and the like) still runs when the page opens. A host you trust from the dialog skips it, unless the link carries a warning; an IP address, an `xn--` host, plain `http` and the address you open CuliBox on can never be trusted, and a link to that address always asks, so an agent's link cannot open a signed-in CuliBox page without the dialog. Only this page's signed-in browser session can add or remove a trusted host through CuliBox, never a device token; each change is written to the audit log first, and Settings › Trusted hosts lists and removes them. A host-tier agent runs as you, so it can edit `link-trust.json` directly and make its own links skip the dialog, as host-tier agents can read the store; boxed agents cannot reach the file. A host session already runs with your full access.

**Never bind CuliBox to a public interface without a front door.** A reachable CuliBox is a remote shell. If you need access from elsewhere, keep the bind on loopback or a private network and put an authenticating proxy or tunnel in front (add its hostname to `allowed_hosts`). Do not rely on the login page alone on the open internet, and use a long password.

## Known limits

- The `host` tier is not contained. A host session is you, with an agent.
- A profile with bindings (AWS, GitHub, tokens) cannot be saved with `runtime: "host"`, but a session of it can be started on Host from New session, or through the API with `host_drops_bindings: true`. There its bindings are a **guardrail, not a boundary**: the broker serves that one session over its own unix socket in a per-session folder under `broker/h/` in CuliBox's data directory, and the session's environment points AWS, `git` and `gh` at it, so the bindings are the default credentials. Nothing stops the agent from using anything else you can reach. It keeps your full access to this machine, and the Host card and the confirm say so, and that your shell's rc files can override the bindings (see below). Host sessions are audited like box sessions, with the tier recorded on each row. CuliBox changes nothing on the host for this: no edit to your AWS config, git config, `gh` login or shell rc files, only environment variables of that session and files in its own folder, which are removed when the session ends. To keep the agent on the bindings, the session also hides what it can without touching your files: it uses its own AWS config and an empty AWS credentials file (so `~/.aws/credentials` does not apply), a per-session `gh` config folder (your personal `gh` login is hidden), and `git@github.com:` and `ssh://git@github.com/` remotes are rewritten to HTTPS, where CuliBox's git helper answers; an empty helper entry for `github.com` comes first, so your own git credential helpers do not answer for it. Token values are never put in the session's environment: `agentbox-env` fetches them per command, as in a box.
- Context paths, the egress allowlist and the box-only options do not apply on Host: a Host run drops them. The profile's own `env` and `secrets` still reach a host session (only box-only names are dropped), so a token you put there, a `GH_TOKEN` for example, is in the agent's environment on Host; the Host card and the confirm list them under "Still on Host". The helpers are `node` scripts: when `node` is not on the session's PATH, the session starts on Host without its bindings and says why (the Access tab lists them as dropped). A Host start of a bound profile needs your confirmation (`host_drops_bindings: true`). `box_only: true` refuses Host by every route, and the confirm does not lift it.
- Bindings on Host can be overridden, and the broker's credentials can be read, by anything that runs as you. The agent's shell loads your rc files, which can export `AWS_PROFILE`, `GH_TOKEN` or `GITHUB_TOKEN` again or put the real `gh` ahead of CuliBox's on `PATH`. Any process of your user can read the session's `AGENTBOX_BROKER_TOKEN` and fetch credentials while the session lives, and can read CuliBox's store and data directory directly. A git rule of your own such as `url."git@github.com:".insteadOf=https://github.com/` still sends HTTPS remotes over your SSH key: CuliBox does not override it, and a `pushInsteadOf` rule of your own sends pushes the same way. The git settings come through `GIT_CONFIG_COUNT`, which git older than 2.31 ignores: there git uses your own credential helper and your SSH remotes, with no sign of it. A `base: login` shell may reset `PATH` (Debian's `/etc/profile`, macOS `path_helper`) and drop CuliBox's `bin` folder from the front, as an rc file can. Use a box when you need a boundary. A Host socket path is capped at 107 bytes on Linux and 103 on macOS (`sun_path`); a data directory whose path is too long makes the Host start fail closed with the path in the message.
- A Host session's write grant checks that no box uses its folder, and while its write credentials may be valid no box of this CuliBox can start in that folder. That hold does not survive every restart of CuliBox: a Host session that had already ended before the restart is not held again, although write credentials it was given may still be valid for up to 15 minutes, and if the broker does not start after the restart no Host session holds its folder. When Docker (or the Mac's VM) does not answer, the grant assumes no box is running and goes ahead. A Docker daemon with live-restore, whose containers keep running while it is stopped, or a remote `DOCKER_HOST` that cannot be reached breaks that assumption.
- The adversary in scope is an agent running arbitrary userspace commands in a box. A kernel-level escape is out of scope.
- On Linux, boxes reach other networks only through CuliBox's CONNECT proxy: port 443, hostnames only, never private addresses or addresses on the host's own interfaces. The exception is the host itself: a box may reach a host service listening on all addresses directly, through its network gateway, and the proxy does not see that (see [Services on this host](#host-services)). A public IP that is NAT'd to the host but not on one of its interfaces is not known to CuliBox. Bound boxes are limited to an allowlist (a profile can add hosts with `egress_allow` or opt out with `egress_open`; see [docs/CONFIG.md](CONFIG.md)): `api.anthropic.com`, `*.amazonaws.com`, `registry.terraform.io`, `releases.hashicorp.com`, `github.com`, and the Go and npm registries `proxy.golang.org`, `sum.golang.org` and `registry.npmjs.org` (`proxy.golang.org` serves any public module on request, so it is an accepted exfiltration channel). `proxy.golang.org` redirects larger module downloads to `storage.googleapis.com`, which is left out on purpose: it serves every Google Cloud Storage bucket, so it would be a bulk exfiltration channel. A profile that needs those modules adds it with `egress_allow`, and accepts that risk for its boxes. Boxes on the egress network cannot reach each other. The proxy caps the connections it holds open, in total and for any one box, so one box cannot use up the others' connections. On macOS every box gets this treatment, bound or not, through a relay in the VM (see [docs/MACOS.md](MACOS.md#every-box)); egress verified on a Mac on 2026-11-02.
- A box workspace is refused when the folder is the filesystem root, a system folder (`/etc`, `/proc`, `/sys`, `/dev`, `/boot`, `/usr`, `/System` or `/Library`), a folder inside or above one of those, `/var` itself or a folder above it, `~/.ssh`, `~/.aws` or `~/.gnupg`, or a folder that contains them (so also any folder above your home). A project inside `/var`, such as `/var/www/app`, is allowed. A host session may still run in such a folder: that is uncontained on purpose.
- The web UI can read and write under your home folder and under each workspace root (Files, git and search). A root is added only by a browser request from this page's signed-in session: a Start in a folder outside every root adds that folder (the repo top when it is inside a repo), or you add one in Settings › Workspace roots. A device token, and so any agent, cannot add or remove one, and a box has no cookie. Each add and remove is written to the audit log before the list is saved, and fails closed: when the audit cannot be written, nothing is added. A folder is never made a root when it is the filesystem root, `/var` itself, or a folder above `/var` or above your home folder, or when it is, is inside or is above any of these: a system folder (`/etc`, `/proc`, `/sys`, `/dev`, `/boot`, `/usr`, `/System`, `/Library`), `~/.ssh`, `~/.aws`, `~/.gnupg`, CuliBox's own data folder. A project under `/var` is fine. Files applies the same check every time it reads the list and Settings does too, so a hand-edited entry for such a folder is not served and Settings lists it as not available. A host agent can edit `workspace-roots.json`, but a host session already runs with your full access. A host session may still run in a refused folder; it just never becomes a root. Removing a root does not stop sessions running in it. `GET /api/workspace/check` also answers a device token: for one given path it says whether it exists and is a folder, which root already covers it, and the folder that would become the root (the repo top when the path is inside a repo). It never lists what a folder holds.
- The New session picker's "Other places" list comes from a scan that, only for a `GET /api/workspace-roots` from this page's signed-in browser session (a device token gets an empty list and triggers no scan), reads the names of folders (never file contents) under a fixed set of bases (`/srv`, `/opt`, `/data`, mounted volumes, and on macOS `/Volumes`), at most 3 levels deep, 1 s, cached for 5 minutes. It skips symlinked folders and any folder a root may never be (above), and lists only folders that hold a project marker such as `.git`. Listing a folder there adds nothing; only a Start in it does.
- When a box starts, CuliBox checks inside it that the workspace and its read-only guards are the folder and files that passed the checks. If any part of the path changed in between, the box is removed before the agent starts and the spawn is refused; spawn again. A box that already runs is checked for its workspace on every new session; on a mismatch an idle box is removed, and one with running sessions is kept and the spawn refused until they end. Its guards are checked only when the box is created, because an editor that saves a guarded file by replacing it changes the file's identity on the host while the running box keeps the old one. For the same reason, a guarded file or folder that you rename or replace on the host after the box started stays as it was inside the box, and the box does not see the new one; that takes an actor on the host, which is outside the threat model above. On macOS a real folder moved into place before the box VM reads the path is taken as the path you listed (see [docs/MACOS.md](MACOS.md#workspace-identity)).
- A box started in place sees the workspace root's `.git`, `.claude/` and any top-level `CLAUDE.md`, `CLAUDE.local.md`, `AGENTS.md` or `.mcp.json` read-only, so it cannot commit there or edit them. Repos with submodules, or whose git config sets `core.worktree` or `core.bare` to anything but false, are refused. When `core.hooksPath` is nested (for example `.husky/_`), the whole top-level directory that holds it (`.husky/`) is read-only in the box. macOS uses the same guard. A default macOS volume ignores case, so the read-only mount of a guarded file would not stop the box writing it under another spelling, such as `claude.md`; there CuliBox also locks those files (and a worktree's `.git` file) on the Mac with `chflags uchg` while the box runs, which you then cannot edit either (see [docs/MACOS.md](MACOS.md#in-place-guard)).
- Those guards cover top-level names only, and block direct writes to them only. They do not make a workspace safe to hand back to the host:
  - The same names in subdirectories are writable: a box can edit an existing `sub/CLAUDE.md`, `sub/.mcp.json` or `sub/.claude/settings.json` (hooks), and a host session started in `sub/` loads them.
  - A box can create an absent `CLAUDE.md`, `CLAUDE.local.md`, `AGENTS.md` or `.mcp.json`, and a new `.git` anywhere in the workspace, including its root when it is not a repo. Servers in a new `.mcp.json` still need Claude Code's project-MCP approval, unless you auto-approve project servers.
  - A read-only file can still run writable workspace code: a git hook that calls a repo script or reads a tool config such as `.pre-commit-config.yaml`, a `.claude` hook that runs `./scripts/…`, an `@import` in `CLAUDE.md`.
  - On Linux, a hooks path or git path that reaches the workspace through a host bind mount of one of its folders or files is recognised as inside it from CuliBox's mount table when the box is set up, and is made read-only or refused like the same path spelled in the workspace; if that table cannot be read, in-place boxing is refused. Not recognised: a mount made after the box starts, one that exists only in another mount namespace than CuliBox's, a mirror that is its own filesystem (a FUSE mount such as bindfs), and a host file that is a hard link to a workspace file. On macOS CuliBox reads no mount table, so a folder of the workspace mirrored elsewhere is not recognised there (see [docs/MACOS.md](MACOS.md#in-place-guard)).
  - So after a boxed session, review changes and untracked files (`git status`, `git diff`) before you run host git or a host-tier session there.
- CuliBox does not scan files for malware, and nothing it shows means a file is safe. Open anything you do not trust (a downloaded file, a repo you did not write, a book or archive an agent fetched) in a box, not on the host, and review what a box hands back before you run it on the host. When a box hands files back, CuliBox flags six kinds of file for you to review: executables (including shared objects and object files), scripts with an exec bit, programs, scripts or archives disguised as documents, images or text (by extension), archives, files with the setuid or setgid bit (a box started in place only, because git cannot carry those bits), and symlinks that point outside the workspace (including one whose target steps back out of another path, such as `s/..`, which the text alone cannot place). The flags show in the toast when a clone's branches come home and in the output of `culibox clone fetch`, when an in-place session exits or its box stops, and as a badge on the profile and an entry in the sidebar. They stay until you mark them reviewed. A flag is a signal to review, not a verdict, and CuliBox still does not scan for malware: an unflagged file is not a safe file. The checks classify a file from its first 8 KiB, hash a flagged file up to a size limit, never run or unpack a file, and have caps on files, bytes and time. When a scan hits a cap it says so on the record instead of showing a shorter list as if it were complete; a later scan does not go back for the files it did not reach, so review what was handed back yourself when you see that note. A workspace over the entry cap (500,000 entries) or the 30-second walk budget stops at about the same place on every scan, so the files past it are never checked and the note comes back each time; run such a project in a clone box, where the check reads the returned commits instead of walking the folder. For a box started in place, the check covers files changed (by inode change time) while the session ran, and reaches back to the last check when the box was not completely checked when it stopped, so it can also flag changes you made on the host in that time. A workspace that could not be checked (its path could not be confirmed when the box started, or its box stopped with no earlier check on record) gets a record that says so instead of a silent gap. A file you marked reviewed is flagged again if its content or its flags change; a file CuliBox could not hash is flagged again every time.
- Boxed sessions that run with your personal config (the default account, or an account with `inherit_personal`) skip Claude Code's "Do you trust this folder?" dialog: when such a session creates its box, CuliBox pre-accepts the dialog for the box's workspace. Those sessions start with `--setting-sources user`, so a repo's own `.claude/settings.json` (hooks, `env`) is not loaded either way. Other boxed sessions, and host sessions, still show the dialog, because there it is the only gate before a repo's hooks run with the agent's credentials in reach. Trust lives in the box home and outlasts the spawn that set it, so a claude that starts there later without `--setting-sources user` also skips the dialog and loads the repo's settings: one run when the config bundle fails to build (CuliBox logs it) or is turned off, after `inherit_personal` is switched off for an account, or one you start by hand in a boxed shell.
- A boxed session that runs with the bypass option (Permission mode: Bypass, which passes `--permission-mode bypassPermissions`, or the older `--dangerously-skip-permissions` bool) starts without Claude Code's one-time "Bypass Permissions mode" warning. When such a session creates its box, CuliBox marks the warning as accepted in the box's home. The option you chose for the profile or the spawn is the consent, and a box is the sandboxed container with restricted network access the warning asks for. Without this, an unattended session (an API spawn with a first prompt) waits on that dialog forever. The acceptance stays in that box home, and Claude Code treats it as consent for any later bypass-mode claude in the same box: a profile whose bypass option you switch off later, another profile that shares the box, and a claude you start by hand in a boxed shell. Clicking "Yes" in the dialog stores the same thing. It is set only when CuliBox creates the box, so a bypass session that joins a box started without the option still sees the dialog. Host-tier sessions are unchanged and still show the warning.
- The option "Skip the critical-rm prompt" sets `CLAUDE_CODE_EVEN_MORE_DANGEROUSLY_SKIP_PERMISSIONS`, which turns off Claude Code's last stop in bypass: the 2-minute wait before an `rm` of the working folder, `~` or `/`. The option sets it only on a boxed spawn that also bypasses; with any other mode the option is dropped and reported. A box profile's own `env` row or secret can also set it, and CuliBox passes that through to a boxed spawn unchecked; it changes nothing unless the session also bypasses. On the host it is stripped from every source CuliBox controls (the profile's options, `env` and secrets, the daemon's own environment, and a login shell's rc files through `env -u`; Claude Code's own `settings.json` env block is outside that), a spawn that asks for it there is refused, and a profile that sets it by `env` or secret drops it when you start that profile on the host. In a box started in place the workspace is your own folder mounted live, so the agent can delete it, and everything in it, without asking.
- A box home that holds Claude Code conversations is never removed automatically, so whatever those transcripts hold (output of commands the agent ran, secrets it read) stays on the host until you delete the home. A box decides this for its own home: an agent can keep its home, and the files it left there, by writing a conversation file. `culibox doctor` lists every home kept this way, with its size.
- It is a single-user tool. There are no roles or per-user permissions.
- The box image `box setup` pulls by default is fixed by digest in the release binary, so Docker checks every byte against that digest, and the release workflow attests the binary when the repository is public. The image itself carries no attestation, and CuliBox does not verify one on pull. Whoever can push to the `ghcr.io/culiops/culibox` package controls what a new `dockerfile-<hash>` tag points at; the release's label check shows the image was built from the same Dockerfile, not who built it. To avoid the pull, build locally (`box_image` set to `culiops/culibox:base`, or `box setup -rebuild`).
- The `abduco` next to the `culibox` binary runs only when no other account can change it or its folder (see `abduco_bin` in [docs/CONFIG.md](CONFIG.md)). A group-write bit counts as yours when the group is named like your user (a private group, as umask 002 systems set up): CuliBox trusts that name and does not check who else is in the group (on macOS users share the group `staff`, so this rule never applies there). Access lists are not read: on Linux a POSIX ACL shows only as the group bits, and macOS ACLs (`chmod +a`) are ignored.
- Sessions that share one box (same workspace and same AWS connections) can read each other's process environment, so attribution between them is best effort. Two sessions in the same folder share it read-write, so a session without the AWS binding can plant a file that a bound session then runs. Give a bound session its own workspace.
- The read scope denies a fixed set of data classes: S3 objects outside `s3_read` (S3 Access Grants credentials included), Secrets Manager secret values, Parameter Store values, DynamoDB items (stream records included), and KMS decryption other than through S3. Every other data store stays readable by design, because an investigation needs it: Kinesis Data Streams records (including copies of DynamoDB items a table delivers to a Kinesis destination), SQS messages, CloudWatch Logs events, Athena and Glue results, Lambda code URLs and others. All of it can reach a transcript. Use the broker with a sandbox or lab account for now, not production.
- An AWS write window is broader than the read scope. Bucket policies, ACLs and public access blocks are denied in the window except on box buckets (`elevate.box_bucket_prefix`), so the agent can make a box bucket public, including one a human created with that name. Code run as a passed role (`elevate.pass_role_prefix`) is not bound by the window's limits, and with `elevate.allow_iam` the agent can create and use its own roles, so the data-read blocks are advisory in that window. The grant panel says what each window allows. Grant write windows only on accounts where that is acceptable (see [docs/aws/agent-role/README.md](aws/agent-role/README.md)).
- S3 Express One Zone directory buckets are never readable through an AWS connection: both the read scope and a write window deny `s3express:CreateSession` on every directory bucket, and `s3_read` does not reach them. A write window also denies setting directory bucket and access point policies, and deleting a directory bucket policy. A stack that reads or writes objects in a directory bucket cannot apply in a write window ([#323](https://github.com/culiops/culibox/issues/323)).
- In an AWS write window, the resource policies of DynamoDB tables and streams, Systems Manager parameters and Secrets Manager secrets cannot be written or removed, but KMS key policies and grants can change: on their own they give another account no item, parameter or secret value, and blocking grants would break common deployments ([#324](https://github.com/culiops/culibox/issues/324)).
- An AWS write window does not deny these classes yet. Closing them needs a redesign of the window's session policy, which is at STS's size limit ([#331](https://github.com/culiops/culibox/issues/331)):
  - Some IAM writes, even with `allow_iam` off: the window denies IAM writes by verb (Create, Delete, Put, Update and others), and calls with other verbs pass. Among them are calls that reset or upload credentials for an existing IAM user, such as a service-specific credential reset or a signing certificate upload. Those credentials are long-lived and outlast the window.
  - STS token calls other than assuming a role and getting a federation or session token, such as service bearer tokens.
  - DynamoDB items can reach the agent through a Kinesis destination the window sets up on a table, although the window denies item reads.
  - S3 access points: deleting an access point policy (directory bucket access points included), and setting an access point's public access block.
  - If one of these matters for an account, deny it in an inline policy on the write role, and keep that role's name starting with `agentbox-` (as the setup in [docs/aws/agent-role](aws/agent-role/README.md) names it): an explicit deny there applies in every window, and the window's own credentials cannot edit a role with that name.
- While a session may hold AWS write credentials, no other box of the same CuliBox can start in its folder, also after the session ended. That hold compares workspaces only: another profile's `context_paths` that include the folder still mount it read-only into that profile's boxes, before or during a window. Another CuliBox instance on the same Docker daemon is held only while the session's box exists, not after it is gone. The hold after a session ended is kept in memory, so one whose box was already removed before CuliBox restarted no longer holds its folder after the restart. Keep a write-capable session's folder out of other profiles' `context_paths` ([#333](https://github.com/culiops/culibox/issues/333)).
- The credential broker holds access to your SSO session. Treat the machine running CuliBox accordingly.
- Persistence covers the daemon restarting, not the whole container or machine being destroyed. After a restart the terminal repaints, but earlier scrollback is not replayed.
- Claude Code is the supported agent.

## Services on this host (Linux)

The proxy does not cover the host itself. A box's network gateway is the host, so a box may open raw TCP or send UDP to a host service listening on all addresses (`0.0.0.0` or `::`), and those connections are not audited. A service bound to `127.0.0.1`, or to one address other than the box network's gateway, is not reachable. A service bound to that gateway address is reachable, and is not listed. `culibox doctor` lists the ports, and the daemon logs them at startup. The list can include ports a box cannot actually reach, such as Docker-published ports and IPv6-only sockets, and outbound-only UDP sockets. Bind anything a box must not reach to `127.0.0.1`. On macOS every box's gateway is the VM, so this does not apply to it.

The proxy itself listens on TCP at the box network's gateway address. While CuliBox is stopped, another account on the host can take that address and port. A box that is still running would then send its proxy connections, and the proxy credentials bound to that box's address, to that account, which could act as the proxy and so bypass the allowlist. The credentials are bound to box addresses and are no use from the host, but acting as the proxy is. CuliBox does not prevent this. When it starts and finds the port taken, it logs that and the proxy does not start: new fenced sessions are refused until the other process is gone, and running boxes keep sending their proxy connections to whatever holds the port. `culibox doctor` reports a FAIL for the `egress port` row while another account has a socket listening there, also when CuliBox is not running. That covers a socket on the gateway address, on all addresses, and on all IPv6 addresses (which takes IPv4 connections too unless it is IPv6-only; `/proc` does not say). Only an account other than yours is reported; run as root, doctor gives a warning instead, because it cannot tell CuliBox's own socket from another account's. Run CuliBox on a host where you trust the other accounts, or do not leave boxes running while it is stopped. On macOS this does not arise: the proxy listens on `127.0.0.1`, and the relay in the VM forwards a box's connection only after the listener proves it holds the relay key.
