# Configuration

Everything CuliBox writes lives in one data root: `$CULIBOX_HOME` (an absolute path), else `~/.local/share/culibox`. The config is read from `<data root>/config.json`, or from `-config <path>`. A `config.json` in the current directory is deliberately never read. The data root and config file must be owned by you and not writable by others.

**Root rules.**
- `AGENT_BOX_HOME` is the deprecated old name of `CULIBOX_HOME`. It still works and prints a notice. If both are set to different paths, CuliBox refuses to start. A root set by either variable is used as it is and never moved.
- With neither set, CuliBox looks at `~/.local/share/culibox` and at `~/.local/share/agent-box`, the root from before the rename. Only the old one exists: it is used in place. Only the new one exists, or neither: the new one. The old path is a link to the new one (what a move leaves behind): the new one. Both exist with different content: CuliBox refuses and names both; set `CULIBOX_HOME` or move one aside.
- Only `culibox serve` moves the old root to the new one, once, and keeps the old path as a link. It moves only when all of this holds: no root variable and no `-config` flag; the old root is a real directory (not a link or mount point) on the same filesystem, and the new path is absent or empty; no other `serve` is running on it; no session is running; the config file in use does not set `data_dir`, and neither it nor `<old root>/credentials.json` names a path inside the old root (a plain text match); and, on a Mac, there is no box VM in it (see [macOS](MACOS.md#configure)). Otherwise the old root stays in use and `serve` logs why; the next start tries again. `doctor`, `store`, `clone`, `box` and `bug-report` never move anything.
- `serve -config <file>` never starts a move: the move only reads the default config, so it cannot tell whether your file names paths inside the root. It does finish a move that was interrupted (the new root still holds `.culibox-move`), because finishing one reads only that file and the default config, not yours, but only when your file uses the new root (no `data_dir`, or a `data_dir` naming `~/.local/share/culibox`). With any other `data_dir` that root is not protected from your boxes, so the move is left, logged, for a start that uses that root.
- Without `CULIBOX_HOME` and `-config`, the config file is the first that exists of `<data root>/config.json`, `~/.config/culibox/config.json` (`$XDG_CONFIG_HOME/culibox/…` when that is absolute), and the old `~/.config/agent-box/config.json`. If there is no `<data root>/config.json` and both `~/.config` files exist and differ, CuliBox refuses. When no root variable and no `-config` is set, the data root resolves, and no other `serve` holds it, `serve` also moves the old `~/.config/agent-box/config.json` into `~/.config/culibox/` and leaves a link, even if the data root itself stays in place; other files there stay. It does not move the file when `~/.config/culibox` exists but is a link, not a folder, or a folder that is not yours or that others can write; `serve` logs why.

| `env_label`, `env_color` | unset | Badge shown in the UI. |

`culibox init` ([macOS](MACOS.md#what-culibox-init-does)) writes these keys for you, after showing the file or a diff and asking: `default_runtime` (`box`), `default_cwd` (the workspace folder you picked), `box_vm_cpus` and `box_vm_memory_gib` (the VM size, macOS only), and `account` (`claude-box`) on each `claude` agent that has none. A `claude` agent already linked to another account is left as it is, and when there is no `claude` agent it adds one. It rewrites the file with sorted keys and two-space indent, and writes it atomically, mode 0600, never through a symlink. Its file is the `-config <path>` you pass (it must already exist: CuliBox stops on a missing `-config` file before init runs), else the config CuliBox already reads, else `<data root>/config.json`, which init creates when there is none.

`box_pids_limit`, `box_tmp_size`, `box_memory` and `box_cpus` apply to boxes created after a restart; a running box keeps its limits until it is recreated.

Make and edit profiles in the UI (Settings › Profiles); `agents` in `config.json` is the file form, and both work. Profiles made or edited in the UI are saved to `profiles.json` in the data root (or at the path set by `profiles_path`) and override a profile of the same name from `agents`. CuliBox reads that file when it starts. You can edit it by hand while CuliBox runs, but the next save or delete of a profile from the UI is then refused until you restart CuliBox, which loads your edit. A save from an editor that was opened before another change to the same profile is refused too: reload the profile and save again. After an update, a page that was open before it must be reloaded before it can save a profile.

Each entry in `agents` takes `name` and `bin` (required), plus `args`, `base`, `env`, `options`, `runtime`, `box_only`, `default_cwd`, `account`, `replyable` (the default for the reply opt-in of its sessions, Claude Code only), `aws_connections` (see [Several AWS accounts in one session](AWS.md#several-aws-accounts-in-one-session)), `github` (see [GitHub access for agents](GITHUB.md)), `tokens` (see [Static tokens for agents](STATIC-TOKENS.md)), `clone_of`, `clone_share` and `clone_no_auto_return` (see [Clone mode](CLONE-MODE.md)), `context_paths` (see [Reading other repos](CONTEXT-PATHS.md)), `imports_off` (see [CLAUDE.md imports](CLAUDE-MD-IMPORTS.md)), `egress_allow` and `egress_open` (below). `box_only: true` refuses every host spawn of the profile, by any route (a per-spawn `runtime: "host"`, the profile's own tier, or an instance with no box layer). It cannot be combined with `runtime: "host"`. Saving a profile with `runtime: "host"` that has bindings, context paths or a clone setup is refused, but a session of a boxed profile can be started on Host. On Host the bindings, context paths and box-only settings do not apply, and the agent runs with the machine user's own access plus the profile's own `env` and `secrets` (the profile view lists those names in `host_keeps`). A spawn of such a profile on Host needs `host_drops_bindings: true` in the `POST /api/sessions` body (New session sends it after you confirm); without it the spawn is a 400 that names the field and lists what would be dropped. A session records what it dropped in `host_dropped`. On an instance whose `default_runtime` is `host`, a `box_only` profile with no `runtime` still saves, but each spawn must ask for the box. `base` is the environment policy: `inherit` (the default; the daemon's environment minus Claude session markers), `clean` (a minimal environment with only what you grant by name) or `login` (run through `$SHELL -l`). `egress_allow` is a list of hosts (exact, or `*.suffix`; at most 32) added to the egress allowlist of a box that has a credential binding; `egress_open: true` lets such a box reach any public host on port 443 (private, tailnet and host addresses are still refused, and every CONNECT is still audited). Both need `runtime: box`, are part of the box key (profiles with different policies never share a box), and have no effect without a binding, since an unbound box already reaches any public host; saving a profile that sets either without a binding returns a warning. Go in a bound box: `proxy.golang.org` redirects larger module zips to `storage.googleapis.com`, which is not in the default allowlist because it serves every Google Cloud Storage bucket (see [SECURITY.md](SECURITY.md)); add `storage.googleapis.com` to `egress_allow` if `go mod download` fails on such a module. Top-level `options` define the launch toggles. A profile only honours per-spawn overrides for options it lists, with one exception: an enum option with `offer_unset` is pickable on every profile whose `bin` it applies to, starting blank (the agent's own default). `offer_unset` defaults to true for `model`, `effort` and `effortLevel` and false for every other key; set it to false to turn that off, and never set it on an enum whose choices grant a capability (`permission_mode` is the built-in example, so it is never offered unset). Bool options are never offered unset; `POST /api/sessions` reports any it ignored in an `options_dropped` list of `{key, reason}` in the 201 body. `POST /api/sessions` also takes a `clone` field. Absent, the profile decides. `false` runs the profile in place, without `clone_of`, `clone_share` and `clone_no_auto_return`: in a box its bindings, egress policy and context paths still apply, and you send `cwd` with it. `true` needs the profile's clone setup and the box; combined with `runtime: "host"` it is a 400, "a clone runs only in a box". A host spawn refused because the profile is `box_only`, or because it turns a box-only option on, returns the reason in the error. Images are instance-wide: set `box_image`.

## Launch options

Every `claude` profile offers four launch options without any `options` in this file:

| Key | Choices | Passed as |
|---|---|---|
| `model` | `fable`, `opus`, `sonnet` or `haiku` (Claude Code's aliases, so each always means the latest model of that family) | `--model` |
| `effort` | `low`, `medium`, `high`, `xhigh` or `max` | `--effort` |
| `permission_mode` | `manual`, `acceptEdits`, `auto`, `plan` or `bypassPermissions` (shown as Manual, Accept edits, Auto, Plan and Bypass) | `--permission-mode` |
| `skip_critical_rm_prompt` | on or off | the environment variable `CLAUDE_CODE_EVEN_MORE_DANGEROUSLY_SKIP_PERMISSIONS`, box only (see below) |

`model` and `effort` start blank, which leaves the choice to Claude Code. `permission_mode` and `skip_critical_rm_prompt` grant a capability, so neither is ever offered unset: a profile offers them only once it sets a default for them (`"options": { "permission_mode": "plan" }` on the agent, or the Permission mode row of a profile made in Settings). Pick them per session in New session, or set a default on the Agent row of a profile made in Settings (a profile defined in this file takes its defaults from its `options`).

Your own `options` are added to these. An entry whose `key` is `model`, `effort` or `permission_mode` replaces the built-in one as a whole, for example to pin full model IDs; an `effortLevel` entry takes the place of `effort`.

Permission mode: Bypass runs every action without asking. Even then, Claude Code stops before an `rm` of the working folder, `~` or `/`, waits 2 minutes and refuses. `skip_critical_rm_prompt` turns that stop off, so it is the most dangerous of the four. It applies only in a box and only together with Bypass:

- It carries `tier: "box"`. An option def takes a `tier` of `""` (the default, any runtime) or `"box"`. A box-tier option is dropped from a host spawn's command, a spawn that turns one on with `runtime: "host"` is refused with a 400 (`"<Label>" runs only in a box`), and a profile whose default turns it on runs on the host without it, once you confirm (`host_drops_bindings: true`).
- On a boxed spawn, CuliBox sets the variable only when the final command bypasses (Permission mode: Bypass, the older bool below, or the profile's own `args`). Otherwise the option is left out and listed in `options_dropped` with the reason `needs Permission mode: Bypass`. Saving a profile that turns it on without Bypass is refused, as is saving it on a profile pinned to `runtime: "host"`.
- On the host, the variable is removed from every environment layer, including the daemon's own environment, and a `login` base runs `exec env -u CLAUDE_CODE_EVEN_MORE_DANGEROUSLY_SKIP_PERMISSIONS ...` so a login shell's rc files cannot set it either. A profile `env` row or secret that names it is dropped the same way when you start that profile on the host.
- In a box started in place, your own folder is mounted live, so with this on the agent can delete it without asking. In a clone, the agent works on its own copy.

`--dangerously-skip-permissions` is not built in: you can still declare it as a bool option, and a profile that does keeps working as before (it loads and spawns with the flag). It is the older form of Bypass. The UI shows it as Permission mode: Bypass and hides its own checkbox, and when a profile sets both, a set `permission_mode` wins and the older flag is left out of the command. A profile that only sets the older bool is offered Permission mode in New session too, so it can move to the enum. A bool option is offered in New session only once the profile sets a default for it.

```json
"options": [
  { "key": "skip_permissions", "label": "Skip permissions", "type": "bool", "flag": "--dangerously-skip-permissions", "bins": ["claude"] }
]
```

## VM folders

On macOS the box VM shares only a list of folders, kept in `vm-shares.json` in the data root: `{"version":1,"shares":[{"path":"/Users/me/code","mode":"rw"}]}`, with `mode` `rw` or `ro`. CuliBox writes this file; it is not a `config.json` key, so do not add it there. Manage it in Settings › VM folders or with `culibox box share list|add <dir> [-ro]|rm <dir>|apply [-force]`. If the file is missing, CuliBox builds it from your profiles on the first run. A change reaches the VM only when applied (a stop and start, about 20 seconds). See [macOS](MACOS.md#vm-folders).

## Workspace roots

The folders the web UI's Files, git and search can open are your home folder (always) and the workspace roots, kept in `workspace-roots.json` in the data root: `{"version":1,"roots":[{"path":"/srv/api","added":"2026-11-21T09:00:00Z","added_by":"web"}]}`. CuliBox writes this file; it is not a `config.json` key, so do not add it there. A folder becomes a root when a session is started in it from the browser (the repo top when the folder is inside a repo), or when you add it in Settings › Workspace roots; remove one there too. At most 32 roots. If you edit the file by hand while CuliBox runs, CuliBox reads it again on the next request. An entry for a folder that may never be a root is not an error: Files does not serve it and Settings lists it as not available. That covers the filesystem root, `/var` itself and any folder above it, a folder above your home folder, and a system folder, `~/.ssh`, `~/.aws`, `~/.gnupg` or CuliBox's own data folder, with anything inside or above those (a project under `/var` is fine). A file CuliBox cannot parse leaves home as the only root, Settings says so, and the next change is refused until you fix or delete the file. See [Security](SECURITY.md#known-limits).

## Trusted link hosts

Links an agent shows open after a confirm dialog (see [Security](SECURITY.md#what-is-protected-and-how)). The hosts you chose to open without it are kept in `link-trust.json` in the data root: `{"version":1,"hosts":[{"actor":"web","host":"github.com","subdomains":false,"added":"2026-11-21T09:00:00Z"}]}`. CuliBox writes this file; it is not a `config.json` key. You add a host from the dialog's "Always open links to …" box (with "and its subdomains" when you want those too) and remove it in Settings › Trusted hosts. At most 200 hosts. A host is a lowercase name with at least one dot; an IP address, an `xn--` name, a port or a trailing dot is refused. If you edit the file by hand while CuliBox runs, CuliBox reads it again on the next request. A file CuliBox cannot parse, or one with an entry it would refuse, trusts nothing: every link asks, Settings says so, and the next change is refused until you fix or delete the file. A file written by a newer CuliBox is not damaged: Settings says so, and the fix is to update CuliBox, not to delete the file.

## Older forms that still load

Configs and profiles written by earlier builds may carry these. They are not the way to set things up now, and none belongs in a new config.

| Older form | What happens now | Use instead |
|---|---|---|
| `AGENT_BOX_HOME`, `~/.local/share/agent-box`, `~/.config/agent-box/config.json` | Still read, with a notice, as described under Root rules. | `CULIBOX_HOME`, `~/.local/share/culibox`, `~/.config/culibox/config.json`. |
| An inline `aws` binding on a profile | Still runs unchanged. The profile editor shows it read-only, and offers **Convert to a connection** or **Remove**. A profile cannot have both an inline `aws` and `aws_connections`. | A named AWS connection, defined in Settings › Credentials › AWS and ticked on the profile. |
| `secrets` on a profile, with `secret_sources` | Still resolved from the environment, a file or the store. The Credentials screen lists these names read-only under **Legacy secrets**. | For the Claude token, an agent account with a pasted token. For other tokens, a static token entry. |
| `box` (`{"box": {"image": ...}}`) on a profile | Ignored when loaded, with a log line; a profile that sets it is refused on save. | `box_image`, which applies to every box. |
| `box_image` unset on an install that still holds `culiops/agent-box:base` | `box setup` and the first box spawn tag that image as `culiops/culibox:base` and keep the old tag. A pinned `box_image` is never touched. | Nothing to do. |
| A `static_tokens`, `github_apps` or `aws_connections` entry written in `config.json` | Still read at start, and shown read-only on the Credentials screen. | Add new entries on the Credentials screen. |
| An agent account with provider `codex` | Still loads, but it cannot launch a session: Codex is no longer a supported agent, and the UI does not offer it. | A Claude Code account. |
