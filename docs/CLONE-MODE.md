# Clone mode

Clone mode lets a boxed agent work on a private copy of one of your repos. Nothing the box writes reaches the original except as a `box/<branch>` branch that CuliBox brings home, by itself or through `culibox clone fetch`, for you to review. One opt-in changes that: a profile can also have the returned branch merged into the branch you have checked out (see [Merging into your branch](#merging-into-your-branch)). It works on Linux and, in the box VM, on macOS (see [On macOS](#on-macos)).

Two profile fields turn it on, and a third is an opt-in for merging work home:

| Field | Meaning |
|---|---|
| `clone_of` | Absolute path of the host repo to copy. It must be a plain git repo with a `.git` directory (no worktree, no `commondir`, no `objects/info/alternates`) whose `.git/config` git can read, not a symlink, and not your home directory or any directory above it. A partial clone (`git clone --filter=…`) works, except in a folder that was once boxed in place before CuliBox classified it (see [below](#a-git-repo-boxes-as-a-private-copy)). |
| `clone_share` | Up to 8 paths, relative to `clone_of`, that the box can read. Example: `["CLAUDE.md", "docs/notes"]`. |
| `clone_merge_home` | Off by default. Turns on the automatic merge of a returned `box/<branch>` into the branch you have checked out in `clone_of`. It needs `clone_of`, cannot be combined with `clone_no_auto_return`, and turning it on asks you to confirm and is audited. See [Merging into your branch](#merging-into-your-branch). |

The profile's `default_cwd` is the clone's directory. The two must not overlap: neither may be inside the other. The profile must be boxed: `runtime: "host"` is refused, and so is a profile that sets no runtime while the instance's `default_runtime` is `host`, both when you save it and when you spawn it. The one exception is a spawn that sends `clone: false` and `runtime: "host"`, which runs the profile without its clone, on the host. `clone: false` with a box tier is refused at a git repo, like any other boxed spawn in place there (see [below](#a-git-repo-boxes-as-a-private-copy)). Picking Host in New session does this for you: the session runs in place in the folder the profile clones (`clone_of`), not in the clone's directory, and the profile's context paths do not apply there. A host spawn of a profile with bindings or context paths needs `host_drops_bindings: true` (New session asks you to confirm), and `box_only` still refuses it. On Host the bindings are the default credentials, not a limit (see [Security](SECURITY.md#known-limits)); the context paths are dropped. Omitting the runtime never reaches the host. A restart keeps the choice. The first spawn creates the clone with host `git clone`. Spawn the session in the clone's root, not a subdirectory.

In the web UI, pick **Work on a private copy** in Settings › Profiles: the folder field is `clone_of`, **Copy lives in** is `default_cwd`, and **Read-only paths** is `clone_share`.

## A git repo boxes as a private copy

A boxed session never runs in place in a git repo. If the folder is a git repo, or a folder inside one (in a repo's work tree), a boxed spawn in place there is refused, and it runs as a private copy instead. In place is only for folders that are not git repos.

- **New session.** For a git folder the "Box · in place" card is disabled ("A git repo boxes as a private copy"). The private-copy card opens a dialog, also for a profile whose copy is of another repo (the dialog then says why it cannot convert). It shows the repo, the copy location (editable; the default is `~/box-clones/<profile>`), the copy's estimated size and the free disk space, and what the box will not see: uncommitted, untracked and gitignored files. When the repo uses Git LFS, its files arrive as pointer files. It names the profile it changes: one click saves that profile as a clone profile (`clone_of` is the repo root, `default_cwd` is the copy location) for good, and starts it. Nothing is copied before that click. When no private copy can be made here (clone mode is unavailable), no card is selected and Start says why: Host is never selected for you, only by a click on its card or for a profile saved as Host.
- **A refused restart, or a phone or API spawn,** opens the same dialog. An API caller gets HTTP 400 with the code `needs_copy`.
- **`clone: false` with a box tier** on a git repo is refused the same way. Host (`runtime: "host"`) is unchanged and always runs in place.
- **Free space.** A first copy is refused when the disk cannot hold it: the free space must be at least the estimated size × 1.1 + 512 MiB. If the estimate fails, the copy goes ahead.
- **Not offered:**
  - A linked git worktree. Run it on Host, or box its main repo as a copy.
  - A folder inside the git repo at your home directory. Run it on Host, or move the folder.
  - A built-in profile, a profile defined in `config.json` (duplicate it in Settings first), a Host profile, or a profile that already copies another repo. Use a separate profile.
  - A profile whose folder (`default_cwd`) is elsewhere, outside the repo. Set the profile's folder to the repo first.
  - The profile "+ Shell" starts: as a copy of one repo, every later "+ Shell" would open in that copy. Use another profile.
- **A shell inside a private copy** (the "+ Shell" beside a box session) still runs there.
- **A folder boxed in place before it was a repo.** A folder that was boxed in place while it was not a git repo can never become `clone_of`, and neither can any folder inside it: a box may have created their `.git`. So boxing a parent such as `~/code` in place blocks every repo under it as a `clone_of`. The refusal names the recorded folder. If you are sure the `.git` is your own, stop CuliBox, set that folder's value under `"git_guarded"` in `<data dir>/boxed-workspaces.json` to `true`, and start CuliBox again. Do not delete the folder's entry: it also keeps the web file API contained in that folder. For a folder CuliBox recorded before this rule and cannot classify, saving a new or changed `clone_of` there asks you to confirm that the `.git` existed before any box ran. The confirmation is audited. Existing clone profiles are not asked. There, a partial clone is refused, confirmed or not: a box may have written the config that declares its promisor remote, and host git would run a command named there.

## What the box gets

| In the box | Mode | What it is |
|---|---|---|
| the clone directory | read-write | The box's own copy of the repo, and the workspace. |
| the clone's `.git` | read-write | Part of that copy. The box commits here. |
| `<clone_of>/.git` | read-only | The original's history, so `git fetch origin` inside the box works. The box cannot change it. |
| each `clone_share` path | read-only | The original's file, shown at the same path inside the clone. |
| the host's Claude memory for `clone_of`, if any | read-only | So the boxed agent starts with what you already told Claude about this repo. |

Claude's memory notes for `clone_of` are readable by the box, which has internet egress. Keep secrets out of them, or set `bundle_source: "off"`, which also turns the memory mount off.

Everything else is as in any boxed session: no host home, no Docker socket, egress only through the proxy (except [services listening on all addresses on this host](SECURITY.md#host-services)).

**Shares are read-only, and readable.** There is no writable share: a `:rw` suffix is refused by name, and so is any other `:`. A share path must be relative and clean, cannot be `.git`, cannot nest inside another share, and no part of its path may be a symlink. The box can read everything you share and has internet egress, so never share secrets. CuliBox warns for names like `.env*`, `*.pem`, `*.key` and `config*.json`, but it does not stop you. A shared `CLAUDE.md` is readable in the box but is **not** loaded as project instructions: boxed Claude runs with `--setting-sources user`. Tell the agent to read it first, or put box guidance in your user-level `CLAUDE.md`. Files the box writes for you (plans, notes) go in a directory inside the clone, such as `docs/handover/box/`, that your `.gitignore` excludes; they never travel in a fetch.

## Bringing code home

Work comes home by itself as `box/<branch>` in `clone_of`, the base branch included. It comes home:

- after each agent turn of the box session, at most every 30 seconds while the clone's refs change. When they have not changed, CuliBox waits until 5 minutes have passed since the last check, so the count of uncommitted files stays current. It judges whether the refs changed from file metadata that the host reads without running git;
- when you start or restart a Host session on the same repo. CuliBox waits up to 20 seconds, then finishes in the background. The toast of a newly started Host session says what came home, how many branches are not home and how many files are not committed (a restart does not show it);
- when the session's agent exits;
- at each spawn of the clone;
- when you press "Bring work home now" in the session.

It moves a ref only as a fast-forward of your `box/<branch>`, and never while you have that branch checked out. When a branch cannot come home, the profile shows "N branches not home" with the reason for each. "Not home" also counts the files in the clone that are not committed: tracked changes and untracked files, but not gitignored files. The count shows on the profile, in the session row and in the Host spawn toast. A count that could not be read is not shown, and a very long list shows as "N+".

CuliBox never commits for the agent. Uncommitted files do not come home, so the boxed agent is told to commit its work on a branch when it finishes a task. The profile field `clone_no_auto_return` turns the automatic return off (the checkbox is "Bring work home automatically", on by default); every trigger above then only reports what is not home. `culibox clone fetch` stays the manual override: it forces the update. "Bring work home now" in the session forces it too, but still never moves a `box/<branch>` you have checked out.

`box/main` can move while you review it. Review the commit the box's handoff names (`git log -p main..<sha>`), not the moving `box/main`.

```sh
culibox clone fetch [-config <path>] [-base <branch>] [-allow-old-history] <profile> <branch>
```

**Pushing to GitHub.** When the profile's GitHub binding can push to the clone's `origin` repository (it has write on `contents`, or it uses a personal access token), CuliBox adds a push-only URL rewrite to the session's git configuration. It is set through the session's environment; nothing is written into the clone. Inside the box, `git push -u origin <branch>` then goes to GitHub, while `git fetch origin` still reads the host repo, and `gh pr create` works. The `box/*` refs come home as usual (unless auto-return is off), whether or not you push. The boxed claude is told this in one appended system-prompt line, and the session shows "work comes home as a PR". Pushes that touch `.github/workflows/` are refused by GitHub for App tokens and for PATs without the Workflows permission (see [GitHub access for agents](GITHUB.md)).

The flags come before the two names. `-base` defaults to `main`. CuliBox makes a git bundle of `<branch>` from the clone inside a throwaway container with no network and the clone mounted read-only, then verifies it and fetches it into `clone_of` as `box/<branch>`, with git's object checks on. The host never runs git against the clone's own `.git`, and this command never merges, even with `clone_merge_home` on: the branch just appears. The command prints the commits that came, a warning for any commit message that carries an AI-attribution trailer, and the review line:

```text
fetched box/feat-x (2 commit(s) not on main):
  abc1234 add the thing
  def5678 fix the thing
review: git -C /home/me/repo log -p main..box/feat-x; merge per your review policy
```

Commit subjects are printed with control characters replaced, because a box wrote them. Bundles over 512 MiB are refused. The container runs the global `box_image`.

**Keeping the clone current.** At each spawn of an existing clone, CuliBox fast-forwards the clone's local `main` (else `master`) from the host, in a throwaway container with no network, and shows the result in the spawn toast and the steer rail. It is best effort and never fails a spawn. It skips a clone that a live session or another instance's box is using, and never touches a checked-out feature branch's work tree. `clone fetch` refuses a branch that carries history host `main` no longer has (for example after a rebase or force-push), or whose clone history CuliBox cannot verify, such as a clone with no recorded base. `clone fetch`, and auto-return, also refuse a branch that carries a commit your repo still holds but no branch or tag there reaches any more. It cannot see a commit that has since been pruned (by any means) and was never a recorded base tip, unless the latest `git filter-repo` `commit-map` names it (a second filter-repo run overwrites that map), nor a commit that was already behind a `box/*` branch when the record was first seeded. `-allow-old-history` overrides these after you have reviewed the branch. A daemon restart aborts a `clone fetch` that is in flight; run it again.

## Merging into your branch

By default CuliBox never changes a branch you work on: the box's work arrives as `box/<branch>` and you merge it. A profile can opt in to a merge instead, with `clone_merge_home` (a checkbox under "Bring work home automatically", which must stay on; the two fields cannot be combined). It is off by default, per profile.

Read the warning before you turn it on. The box's commits then land in your branch with no review step, and anything the box wrote runs with your permissions when you or a tool runs it: a build, a test, a script. The checks below cover files that host tools load by themselves and the scripts and folders those files name. They do not cover every file a person later runs, and [what they miss](#what-the-guard-does-not-cover) is listed below. Turning the switch on in the profile editor shows this in a dialog, and the save records an audit entry, `clone_ack_merge_home`, with the repo. The dialog comes again if you change `clone_of` while it is on. Turning it off needs no confirmation. The profile API refuses the switch without `ack_merge_home: true` on the save. A profile written in `config.json` takes the field without the dialog, because editing that file is your own act.

**When it runs.** After an automatic return, and only then: not for "Bring work home now" and not for `culibox clone fetch`, which stay as they are. It also runs on a return that moved nothing, so a merge refused earlier (a dirty tree) goes through once the cause is gone. It does not run in a pass that could not check the clone.

**Only this profile's own work.** `box/X` in `clone_of` is shared: every profile that copies the repo, and `culibox clone fetch`, write to the same `box/X`. CuliBox merges `box/X` only while it is the exact commit this profile's copy has on `X`, as listed in the same return. A `box/X` that another profile or a manual fetch wrote is not merged, and CuliBox says nothing about it; it stays for you to review.

**The same-name rule.** `box/X` merges into `X` only while `X` is the branch checked out in `clone_of`'s main work tree. `X` can be any name (`main`, `master`, `develop`, a feature branch). Linked worktrees of `clone_of` are not looked at. If `box/X` is not strictly ahead of `X`, there is nothing to merge and CuliBox says nothing.

**The checks.** CuliBox merges only a fast-forward (`git merge --ff-only`), of the exact commit it checked, and only when every check passes. When one fails, `box/X` stays for you to review, and the toast and the profile say why:

| Reason | Shown as | Meaning |
|---|---|---|
| `detached` | the repo has no branch checked out | `HEAD` is not on a branch. |
| `diverged` | X has commits the box does not have | `X` and `box/X` each have commits the other lacks. |
| `dirty` | X has uncommitted changes | A tracked file has staged or unstaged changes, before the checks or again right before the merge. Untracked files do not count here, but git will not overwrite one (see `failed`). An ignored path the commits add is refused as `guarded`. |
| `guarded` | it changes files host tools load by themselves | The commits touch a protected file, a file a protected name links to, a path your ignore rules match, or a submodule (below). Up to 3 example paths are shown. |
| `flagged` | it has files flagged for review | The commits carry a file CuliBox flags when a box hands work back (see [Known limits](SECURITY.md#known-limits)), or the check hit a cap or could not finish. Up to 3 paths are shown. |
| `filter` | it changes files that use a git filter (such as Git LFS) | A changed path has a `filter` attribute. CuliBox runs git without your global config, where such filters usually live, so a checkout would write the wrong content. |
| `moved` | X moved while it was checked | You switched branch or committed while the checks ran. It is tried again on the next return. |
| `failed` | `git refused:` and git's message, or `could not merge:` and the cause | Shown as "git refused" only when git itself refused the merge (an untracked file of yours in the way that the box's commits also add). Any other failure is shown as "could not merge": a git call that failed, a config CuliBox could not read, a scan that hit a cap (`too many paths to check`), a script call it cannot follow (`cannot follow workspace package scripts`), or an audit entry that could not be written. |

The toast for a merge reads "merged box/X into X (n commits, m files)"; for a refusal, "box/X not merged into X: <reason>", once per commit and reason, not on every turn. Toasts can be missed, so the profile shows the switch ("Merges into the checked-out branch") and the last merge or refusal, and the audit log keeps every merge.

**What is never merged.** The guard looks at every commit in the range and at the net difference between your branch and `box/X`, so a file that is added and removed again, or restored by a merge commit the box made, is still seen. Names are matched without regard to case, so `.Claude/` counts as `.claude/`. A change to any of these refuses the merge:

- a file named `CLAUDE.md`, `CLAUDE.local.md`, `AGENTS.md`, `.mcp.json`, `.envrc`, `.gitattributes`, `.gitmodules`, `mise.toml`, `.mise.toml`, `mise.local.toml` or `.mise.local.toml`, at any depth;
- more files that a tool loads on its own, at any depth: `.env` and `.env.*`, anything starting `.envrc`, `.npmrc`, `.yarnrc` and `.yarnrc.yml`, `bunfig.toml`, `pnpm-workspace.yaml` and `.yml`, `.pnpmfile.cjs` and `.mjs`, `.gitignore` (a rule dropped from it would let a later merge add what it hid), `mise.<env>.toml` and `.mise.<env>.toml`, `*.code-workspace`, anything starting `.aider`, and the nix, devenv and devbox files (`flake.nix`, `flake.lock`, `shell.nix`, `default.nix`, `devenv.nix`, `devenv.yaml`, `devenv.lock`, `devbox.json`);
- a git hook manager's config, at any depth: `.pre-commit-config.yaml`, `.pre-commit-hooks.yaml`, `.overcommit.yml`, and lefthook's `lefthook.yml`, `lefthook-local.yml` and their `.yaml` and dot-prefixed (`.lefthook.yml`) forms;
- anything under a directory named `.claude` or `.cargo`, at any depth;
- anything under a top-level `.husky`, `.githooks`, `.vscode`, `.devcontainer`, `.mise`, `mise`, `.config`, `.idea`, `.zed`, `.cursor`, `.gemini`, `.codex`, `.windsurf` or `.continue`;
- `.github/copilot-instructions.md` and anything under `.github/instructions/` or `.github/prompts/`. Other files in `.github/`, including CI workflows, are not on this list (see below);
- a path your ignore rules match, whether the commits add it or change a tracked file there. CuliBox asks git with your rules: every `.gitignore` in the repo, `.git/info/exclude`, `core.excludesFile` and your global ignore file. A new file under an ignored `.venv/` or `node_modules/` is loaded by host tools, so it refuses even though no name on this list matches. A tracked file that an ignore rule matches also refuses when it changes (a force-added `dist/app.js` under an ignored `dist/`); merge those by hand or take the rule out. The names are asked as plain file names, so a name such as `:(glob)x` is not read as git pathspec syntax;
- a file that a `CLAUDE.md` imports with an `@path` line, and any folder above it, because the agent reads it as part of the `CLAUDE.md`. CuliBox reads every `CLAUDE.md` and `CLAUDE.local.md` git tracks in the repo, an untracked `CLAUDE.local.md` and `.claude/CLAUDE.md` at its top, the markdown files under `.claude/rules` (tracked or not), and your `~/.claude/CLAUDE.md`, and follows their imports as the agent does (`~/` is your home, a relative path is relative to the importing file, up to 5 imports deep). Known limit: `CLAUDE.md` files in folders above the repo are not read, so a file inside the repo that only they import is not protected by this rule;
- the folder that `core.hooksPath` names, when it is inside the repo, and any folder above it. CuliBox reads `core.hooksPath` from the repo's config, from your global git config (`~/.gitconfig`, then `$XDG_CONFIG_HOME/git/config` or `~/.config/git/config`, following includes) and from `/etc/gitconfig`, and protects every value it finds;
- the work-tree files that git config loads or runs. CuliBox reads the whole git config your git reads for `clone_of` (the repo's, the global one and `/etc/gitconfig`, with their includes). It refuses a change to a work-tree file that config was read from, to the target of an `include.path` or `includeIf.*.path` (whether or not it exists yet), to the file `core.attributesFile` names (in any config; a relative path is taken against the repo top), and to a program the config runs from the work tree, and to that program's folder (its command line is read as below, plain words and runner manifests included: `diff.x.textconv = node conv` refuses `conv.js` and `package.json`, `core.pager = npx -y prettier` refuses `package.json`). The programs are `filter.*` (clean, smudge, process), `diff.*` (textconv, command) and `diff.external`, `difftool.*.cmd`, `mergetool.*.cmd`, `merge.*.driver`, `core.pager` and `pager.*`, `core.editor`, `sequence.editor`, `core.sshCommand`, `core.gitProxy`, `core.askpass`, `core.fsmonitor`, `interactive.diffFilter`, `credential.helper`, `gpg.program` (also `gpg.<format>.program`), `gpg.ssh.defaultKeyCommand`, and aliases that start with `!`;
- the scripts and folders that your host's agent, direnv, mise, git hook and editor configs name, and each folder they sit in (a top-level script only itself). CuliBox reads, in the repo at its top: `.mcp.json` and `.claude/settings.json` and `.claude/settings.local.json` (MCP server commands, arguments, environment and working folder, hook, status line and helper commands, local plugin folders; every `command` key, MCP `headersHelper`, `fileSuggestion`, `apiKeyHelper`, `awsAuthRefresh`, `gcpAuthRefresh`, `proxyAuthHelper`, `processWrapper`, `sshHostCommands`, `sandbox.ripgrep`, `sandbox.bwrapPath` and `socatPath`, the managed `policyHelper.path`, and `managedMcpServers`), `.envrc` and `.envrc.local` (sourced, watched and loaded files, `use flake`, `use nix`, `use devenv`, and any command on a line), the mise configs (env files, hooks), the files directly in `.husky/` and in a `core.hooksPath` folder inside the repo (every line that is not a comment), the `entry:` values of `.pre-commit-config.yaml`, the `run:` values of the lefthook files, the `command:` values of `.overcommit.yml`, and the command and arguments of every task in `.vscode/tasks.json` (also its `windows`, `linux` and `osx` variants). The same agent configs are read from your account, and the paths they name are taken against the repo: `~/.claude.json` (its user-scope `mcpServers`, and the `mcpServers` of the project entry for `clone_of`, matched by the path or the path it resolves to), `~/.claude/settings.json`, `~/.claude/settings.local.json`, and the managed settings (`/etc/claude-code/managed-settings.json` on Linux, `/Library/Application Support/ClaudeCode/managed-settings.json` on macOS) with the `managed-settings.d/*.json` drop-ins and `managed-mcp.json` that sit next to them. Values in an `env` block are read by key: named command keys (`NODE_OPTIONS`, `PERL5OPT`, `RUBYOPT`, `EDITOR`, `VISUAL`, `PAGER`, `SHELL`, `PROMPT_COMMAND`, `LESSOPEN` and the git program keys such as `GIT_SSH_COMMAND`) are read as a command line, `BASH_ENV`, `ENV` and `PYTHONSTARTUP` as a file, search-path keys (`PATH`, `PYTHONPATH`, `NODE_PATH`, `LD_PRELOAD`, `LD_LIBRARY_PATH`, `DYLD_*_PATH`, `PERL5LIB`, `RUBYLIB`, `GEM_PATH`, `CLASSPATH` and a few more) as lists of folders, and any other key only for words that look like a path. A refusal caused by an env value never shows the value. A command line is read for: any word with a `/`, a leading `.` or a script extension; the command word and the tool a fetcher runs (`npx`, `bunx`, `pnpx`, `uvx`, `pipx run`, `pnpm dlx` and `exec`, `yarn dlx` and `exec`, `npm exec`): each names a top entry and that tool's own config there, any top entry named `<word>.*` or `.<word>*` (`npx eslint` refuses `eslint.config.js` and `.eslintrc.cjs`, `prettier` refuses `.prettierrc.js`, `jest` refuses `jest.config.ts`; not for a one-character word, nor for `git`, `sh`, `bash`, `zsh`, `dash`, `fish`, `env`, `exec`, `cd`, `echo`, `cat`, `test`, `true`, `node`, `python`, `python3`, `ruby`, `perl`, `docker` and `podman`, whose `<word>.*` entries are not their config); the script argument of an interpreter (`node`, `python`, `bash`, `sh`, `deno`, `bun`, `ruby`, `perl`, `php`, `tsx`, `ts-node` and others): it names a top entry and that name with a script extension (`node server` refuses `server`, `server.js`, `server/`), without the `<word>.*` rule; the first part of the module in `python -m a.b` (also `-ma.b`), `uv run -m a.b` and `node --import`, `-r` or `--require a` (`a`, `a.py` or `a.js`, whether or not it exists); the folder after `--directory`, `--cwd`, `--prefix`, `--dir`, `--project`, `-C`, `cd` or `pushd`, which is refused whole, and every path after it is also taken against that folder. Both word rules also match a file the commits add, not only one you have. Subcommands (`npm test`, `docker run`, `gh auth`), flag values (`--browser chrome`) and other arguments are not looked up. When a command calls a task runner (`npm`, `make`, `just`, `cargo`, `uv`, `pip` and others), it also refuses the runner's manifest at the repo top: `package.json`, `Makefile`, `justfile`, `Taskfile.yml` and `Taskfile.dist.yml`, `pyproject.toml`, `setup.py`, `setup.cfg`, `Cargo.toml`, `go.mod` and so on. Any package runner or fetcher call in a host hook, MCP server or git config program value (core.pager, a `!` alias, a filter or diff driver) (`npx`, `pnpx`, `bunx`, `npm exec`, `bun x`, `pnpm exec` and `dlx`, `yarn exec` and `dlx`, `uvx`, `pipx run`) refuses changes to `package.json` or `pyproject.toml`, whatever the package, its version, `-y` or `-p`: a fetched tool, even `prettier@3` or `@playwright/mcp@latest`, still reads its config from the project. So with an `npx` or `uvx` MCP server in your own Claude Code config, a box commit that changes those files never merges by itself; merge it by hand. `docker` and `podman` have no repo config. A call to `npm`, `pnpm`, `yarn` or `bun` also reads the `package.json` script it runs, with its `pre` and `post` scripts and the scripts those call (every script when the name cannot be told), and `make`, `just` and `task` read their whole `Makefile`, `justfile` or `Taskfile` (with the files they include, `-f` files and `just` modules) for the files the recipes run. A make rule's prerequisites that look like a path (`tools/x.sh`, `.tools/q`, `gen.sh`) are always refused. Plain-word prerequisites (`all: build test`, `.PHONY: test lint`) are targets, not commands, and are not looked up, unless a make file the scan reads uses an automatic variable (`$@`, `$%`, `$<`, `$^`, `$+`, `$?`, `$*`, `$|` and their `$(@D)` / `${<F}` forms), `.RECIPEPREFIX` or a computed variable name: then every prerequisite is read as a command (`$(MAKE) -C $@` refuses the folder a prerequisite names). A program a make line runs by path (`./check`) also refuses the files a built-in rule can make it from (`check.sh`, `check.c`). Up to 20000 such header lines are kept for one scan, across all its make files; past that the merge fails. The recipe lines, what follows a rule's `;`, `define` blocks and a rule whose prerequisites call a function or set a variable are always read. A script call that uses workspaces (`--workspaces`, `--workspace`, `-w`, `--filter`, `-r`, `yarn workspace`, `pnpm recursive`, an `npm_config_workspace*` or `npm_config_filter*` setting, or a `workspace`, `filter` key in the repo's `.npmrc`) cannot be followed and ends `failed`. So does any `npm_config_*` or `pnpm_config_*` environment setting on a call to `npm`, `pnpm`, `yarn`, `bun` or `node`, and a `make`, `just` or `task` call whose options hold quoting or substitution CuliBox cannot read (`make -f $(F)`, an unclosed quote, `include $(DEPS)`). This reads more than it needs to on purpose, because a wrong guess only costs a refusal;
- a file that a protected name links to. When `CLAUDE.md`, `.mcp.json`, `.claude` or another protected path is a symlink in your work tree, CuliBox follows it (up to 40 links) to the file it points to inside the repo and refuses a change there, and to each link on the way. The same goes for a script a config names that is itself a link: the file it leads to and that file's folder (not the repo top) are refused. A link that loops, or one it cannot follow, refuses the merge. A protected config that is a link out of the repo (a dotfiles link such as `.claude/settings.local.json`) is read at its target, and a change to the files it names is refused;
- a submodule (a git link);
- a file that uses a git filter, such as Git LFS (`filter`, above);
- a file CuliBox flags (`flagged`, above).

<a id="what-the-guard-does-not-cover"></a>**What the guard does not cover.** It refuses a change only when it can name the file. Treat the merge as a way to skip a review you would otherwise do, and leave it off for a repo whose commits you would not read before running them. These gaps are known:

- Code that a named script imports from elsewhere in the repo. A script named by `.mcp.json` or a hook is protected with its own folder, but a module it imports from another folder is not.
- What a `.env` file names, and what a file that `.envrc` or mise sources sources in turn. CuliBox protects the named file, not the files it names.
- Configs a hook's tool loads that are not named after the tool at the repo top: a config in a subfolder, a config under another name (`lint.config.js` for `eslint`), and settings inside `package.json` or `pyproject.toml` when no runner or fetcher is called (each is refused whenever its own runner or fetcher is called: `npm`, `npx` and the other node runners refuse `package.json`, `uv`, `uvx`, `pipx run` and the other Python runners refuse `pyproject.toml`). A tool's own `<tool>.*` or `.<tool>*` config at the repo top is refused, as above.
- Plain words of subcommands and arguments. `npm test` does not refuse a `test/` folder, `docker run` does not refuse `run.sh`, `gh auth` does not refuse `auth/` and `--browser chrome` does not refuse `chrome`, because only the command word, a fetched tool and an interpreter's script are looked up. A tool that a hook calls through a word in one of those places is not seen.
- A hook or script that runs the whole test suite (`npm test`, `go test ./...`). It runs every test file the box changed, and the guard cannot list them. Only the script that `package.json` names is read.
- Scripts in workspace packages' own `package.json`. A call that uses workspaces ends `failed` (above); a plain `npm run x` reads only the root `package.json`, and `pnpm-workspace.yaml` is protected but its keys are not read.
- A tracked folder that no ignore rule matches, such as a `.venv/` you committed on purpose. A change under it merges. Add it to `.gitignore` or merge by hand.
- Unusual shell syntax in the host's own hooks. CuliBox reads the command lines of files the box cannot change, so a hook written with odd quoting (`ma''ke`, a runner name inside an unclosed quote, `#` comments inside a quoted word) can show a runner it does not see. Where the syntax makes a recipe runner's options unreadable it fails closed instead. A `.envrc` or mise setting of a workspace variable that the hook command itself does not hold is not seen either.
- A file that a command reads through an environment variable other than the ones listed above (an env key that is not listed adds no runner manifest and no script look-up either), and `DYLD_FALLBACK_FRAMEWORK_PATH` and `DYLD_VERSIONED_*` on macOS.
- The macOS managed-preferences profile (`com.anthropic.claudecode`). Only the managed settings file and drop-ins above are read.
- A protected config that is a link out of the repo is checked and then opened by path, so a target that changes between the two can be missed. Only a target you own can change that.
- An ignore file git cannot read. The ignore check cannot tell that from "no rule matches", so such a file hides its rules. A box path that lies beyond a symlink of your work tree ends `failed`.
- Configs below the repo top. A nested `.mcp.json` or `.claude/` is refused by name, but the scripts they name are not looked up. Only the configs at the top are read for the files they name.
- Parts of the hook and editor configs: lefthook's `scripts:` folder, the `args:` of a pre-commit hook, `.vscode/launch.json`, a task's `options.cwd` (a relative script in a task runs against it, and only the repo top is tried), and a `.vscode/tasks.json` that stays unparseable after its comments and trailing commas are taken out (skipped). Hook files are read only in `.husky/` and in the repo's own `core.hooksPath` folder (not in a subfolder of it).
- Your Claude Code config in other places: a config folder that `CLAUDE_CONFIG_DIR` moves, a `~/.claude.json` for another user, and settings of a plugin or an enterprise server. Only the three files and the managed settings above are read.
- Symlinks that are not tracked and sit below the repo top. Tracked links at a protected name and links at the repo top are followed; an untracked link deeper down is not seen.
- Parts of a big repo. These caps refuse the merge (`failed`, "too many paths to check") instead of skipping what is past them: more than 128 config files (64 in one hook folder), 2048 named paths, 200 files read for CLAUDE.md imports, an imported file over 1 MiB, a `.claude/rules` folder with more than 500 entries, 512 package scripts, 20000 lines in one hook, recipe or config file, a folder with more than 4096 entries at the repo top, or more than 64 folders looked up for a word. A config or hook script in the repo that is over 1 MiB, or cannot be read, refuses too, and so does an imported file or a `.claude/rules` folder that cannot be read. An import, or a `.claude` or `.claude/rules` folder, that is a link out of the repo is read at its target. A few inputs are skipped or cut instead. All of them are files you own that the guard does not let a box change (CLAUDE.md files, `.claude/`, the protected configs), so a box cannot use them to hide a file: a config file that is not there or is not a regular file; an import more than 5 hops from a CLAUDE.md, and `.claude/rules` folders more than 4 levels down; a `.mcp.json`, project settings file, `.vscode/tasks.json` or `package.json` that does not parse (the tool cannot load it either); JSON nested more than 24 levels deep in a settings file; and a YAML block (`entry:`, `run:`, `command:`) or mise statement longer than 200 lines. Your own Claude Code config is read the same way: `~/.claude.json` up to 32 MiB and the settings files up to 1 MiB, and a file that is there but cannot be read, is over that size or is not valid JSON refuses the merge (`failed`, "cannot read the Claude Code config"); a file that is not there is nothing. Too many protected paths or files to check for symlinks refuses the merge too.
- CI. A change to `.github/workflows/` or another CI definition is merged, and your CI runs it on your next push.
- Git config in places CuliBox does not read: a system config outside `/etc/gitconfig` (Homebrew's `$(brew --prefix)/etc/gitconfig`, the git that comes with Xcode), and `GIT_CONFIG_GLOBAL` or `GIT_CONFIG_SYSTEM` set in your shell. The global config is found from CuliBox's own environment: `XDG_CONFIG_HOME` is the one the daemon runs with, not necessarily your shell's. If your hooks folder is inside the repo, set `core.hooksPath` in the repo's own config, or keep the folder outside the repo.
- A merge cut off half way. CuliBox ends git after 60 seconds, and git can also be ended with the daemon, for example when a service manager stops everything the daemon started. The branch moves last, so it still points at the old commit, but part of the new files can already be in your work tree and index. `git status` then shows changes you did not make, and a `.git/index.lock` may be left behind. CuliBox does not touch that tree: its next pass reports `dirty`. To recover, check `git status` and `git reflog` (no `culibox auto-merge` entry for the branch means the merge did not finish), remove `.git/index.lock` only when no git is running, then run `git merge --ff-only box/<branch>` to finish the merge, or `git reset --hard` to drop the half-written files (the tree was clean when the merge began, and `--hard` also drops any edit you made since).

**What CuliBox does when it merges.** Every git call runs with hooks off, no replace objects (`GIT_NO_REPLACE_OBJECTS=1`) and none of your global git config, and the merge is of the commit that was checked, not of the branch name. It writes an audit row, `clone_merge_home` (the branch, the old and new short ids and the commit count), before it merges, and `clone_merge_home_failed` if git then fails; if the audit row cannot be written, nothing merges. The branch's reflog says `culibox auto-merge`, so `git reflog` shows which moves were CuliBox's. Once git itself refuses the merge of some commits, the merge of those same commits is tried again at most every 30 minutes, so a lasting refusal does not write an audit entry on every return; the dirty check and the scan are skipped for them inside that window. Any other `failed` (a git call before the merge, a config CuliBox could not read, the audit entry) is tried again on the next return. Commits found to carry flagged files are not scanned again either: they stay `flagged` until `X` or `box/X` moves. Every other refusal is checked again on each automatic return.

**Branches other than `main` and `master`.** The refresh of the clone (see [below](#bringing-code-home)) updates only the clone's `main` or `master`. For another branch, the merge works while you have not committed on `X` since the box's copy of it. Once you do, `box/X` no longer contains your commits: while the box has nothing new on `X` there is nothing to merge and CuliBox says nothing; once the box also has new work on `X`, the reason is `diverged`, until the box brings your commits in and goes on from there.

**Git version.** The merge needs git 2.31 or later on the host (the range check uses `git log --diff-merges`). With an older git every merge ends `failed`, and `box/X` stays for you to review as without the switch.

**A race CuliBox does not close.** If you switch branch in the same instant between its last check and the merge, git still refuses anything that is not a fast-forward and anything that would overwrite a file, but the merge can land on the branch you switched to if `box/X` happens to fast-forward it too.

## Refusals

- A host-tier session is refused anywhere inside a clone, including a subdirectory, a path that does not exist yet, or another spelling of the same directory (a symlink, or different letter case on a case-insensitive disk such as the macOS default). The box wrote those files, and host-tier tools would trust them. A host-tier session at `clone_of` or at a share source is fine.
- CuliBox records every directory it has used as a clone in `<data dir>/clone-dirs`, one path per line. A recorded directory stays box-owned even after its profile is edited or deleted. Deleting the directory does not release it. To release one, remove its line from `<data dir>/clone-dirs`. An unreadable record refuses every host-tier spawn until it is fixed.
- A spawn is refused, never partly started, if `clone_of`, a share source or a mountpoint is unsafe: a symlink on the path, a path inside the data root or a config directory, or an existing clone whose `origin` is not `clone_of`.
- A `clone_of` that is inside another profile's clone, or inside a recorded clone directory, is refused when you save the profile, when you spawn it and in `clone fetch`: the owning box could have planted git hooks there.
- Changing `clone_of`, `default_cwd` or `clone_share` gives the profile a new box rather than reusing the old one.

## On macOS

Clone mode works as on Linux, with the boxes in CuliBox's box VM (see [Running CuliBox on macOS](MACOS.md#boxed-tier-contained-sessions)). The containers that refresh a clone, list its branches and make the bundle for `clone fetch` run in that VM too, never on your own docker.

- `clone_of` must be inside a VM folder (read-only is enough) and the copy's parent directory inside a read-write one: the VM shares only the folders on its list (see [VM folders](MACOS.md#vm-folders)), and the data root cannot hold either. Any other place is refused when you save the profile and when you spawn it, before the copy is made.
- `culibox clone fetch` needs the box VM running and never starts it. With the VM stopped it refuses and tells you to run `culibox box setup` (or start any boxed session) first.
- Leftover clone containers are removed when `culibox serve` starts and the VM is running. While the VM is stopped no container runs in it.
- Files the box writes in the clone are owned by your Mac user.

## Known limits

- When branches come home, CuliBox flags executables, disguised files, archives and outward symlinks, in the toast and in `culibox clone fetch`. It is a signal to review, not a malware scan; see the "CuliBox does not scan files for malware" entry in [Known limits](SECURITY.md#known-limits) in docs/SECURITY.md.
- Never put `clone_of` inside a boxed workspace (or any other directory a box can write): a box could plant git hooks in that repo, and the host runs git there during `clone fetch`. CuliBox refuses a `clone_of` that is inside a clone or a recorded clone directory, and runs its own git calls with hooks disabled, but it cannot see every directory a box can write. A spawn that runs a profile in a box in place (`clone: false`) at your `clone_of` is refused, because `clone_of` is a git repo. A folder that was boxed in place while it was not a repo can never become `clone_of`, because a box may have created its `.git` (see [above](#a-git-repo-boxes-as-a-private-copy)).
- A linked git worktree cannot be boxed: not as a copy, and not in place. Run it on Host, or box its main repo as a copy.
- A box does not see what git does not carry: uncommitted, untracked and gitignored files stay out of the copy. A repo that uses Git LFS arrives with pointer files, not the large files.
- Never run a host-tier agent session in a directory above the clones (for example your home). Claude Code lazily loads nested `CLAUDE.md` and `.claude/` files from any subdirectory it reads, so files a box wrote under a clone could steer a host agent. Keep clones outside every tree where host sessions run.
- Your own shell inside a clone cannot be policed. A box can plant git hooks, config and aliases in the clone's `.git`, so never run git or other host tools there. Review through `clone_of` after a fetch, not in the clone.
- A file you copy out of a clone by hand might be a symlink the box planted, and `cp` would copy its target. Check that it is a regular file first.
- The box and the host share a disk. A box can fill it; there is no per-box quota.
- CuliBox's file editor follows links inside box-written directories. Treat a clone's contents as untrusted when you open them in the UI.
